## 2. Issues the backlog does not cover (ranked)

### Must fix before the first real event

1. **Every guest can see every photo.** `GET /g/{token}/photos` and
   `GET /g/{token}/stream` (`api/routers/gallery.py`) return *all* photos of the
   event to anyone holding the QR token, and the QR token is displayed publicly
   at the event. The guest UI no longer calls them, so they're dead V0 code that
   undoes the face-match privacy model. Also, `minio-init` makes the bucket
   anonymously readable (`mc anonymous set download`). To verify: MinIO's
   read-only policy normally includes `ListBucket`, which would let anyone
   *enumerate every photo of every event* at `http://<host>:9100/solna-media/`.
   → Delete the two endpoints. Make the bucket private and serve signed URLs
   (product decision Q1 below).

2. **Photos are processed before the upload finishes.** The watcher reacts to
   `on_created` and then waits until the size stops changing for 0.5 s, for 5 s at
   most (`watcher/process.py:_wait_until_stable`). A 10–25 MB JPEG over camera
   Wi-Fi regularly stalls for longer than 0.5 s or takes longer than 5 s. The file
   is then ingested half-written, which gives a truncated original, no thumbnail
   and no faces, and it is never retried.
   → Trigger from pyftpdlib's `on_file_received` in the FTP server, which fires only
   once the upload is complete. This is the chosen fix, because it also removes the shared volume (§3).
   The quick alternative is `on_closed` (watchdog 6 exposes inotify
   `IN_CLOSE_WRITE` as `FileClosedEvent`).

3. **Storage keys collide and overwrite earlier photos.** The key is
   `raw/{photographer_id}/{filename}`, but cameras reuse filenames:
   `DSC00001.JPG` comes back after the counter wraps or resets, or after a card
   swap. The key is per photographer, not per event, so event #2's
   `DSC00042.JPG` silently overwrites event #1's in S3, and the old Photo row now
   shows the wrong picture.
   → Put the photo's UUID in the key (`raw/{photographer_id}/{uuid}-{name}`).

4. **A failed ingest is lost for good.** If the API is down (a deploy, a crash),
   `requests.post(...).raise_for_status()` throws, the exception is logged, and the
   photo never reaches the DB. Nothing rescans on startup either.
   → Retry with backoff, and do a startup rescan of files that have no DB row
   (or move processed files to `done/`).

5. **The API event loop is blocked during selfie matching.** `POST /g/{token}/match` is
   `async def` but makes blocking calls: `requests.post` to the face service
   (30 s timeout) and synchronous SQLAlchemy. While one guest's selfie is
   embedded, *every* other request on that worker stalls, including all the SSE
   streams. The two SSE generators also run synchronous DB queries on the loop
   every 3 s. The face service has the same problem (`async def embed` runs
   CPU-bound inference). Selfie bursts at an event will freeze the app.
   → Make `match` and `embed` plain `def`, so FastAPI runs them in its threadpool,
   and wrap the SSE DB polls in `run_in_threadpool`.

### Should fix soon

6. **Selfie matching waits behind photo ingest.** Watcher ingest and guest selfies
   share one single-worker face service. During burst shooting, guests wait behind
   the photo queue. → Fine for the pilot. Later: 2 workers, or a priority
   lane for `/embed` from the API.
7. **An FTP password is lost for good if missed.** Only the hash is stored, and
   there is no regenerate endpoint. → Add "regenerate FTP password" to the camera
   setup page (fits into story 1.3).
8. **The API writes into the FTP volume.** `ensure_photographer_intake_dir`
   (`api/ftp_provision.py`) couples the API to the FTP host's disk. The FTP
   server already creates the directory on login (`ftpserver/server.py`). →
   Delete it. That frees the API to run anywhere (§3).
9. **No limits on `/match`.** It accepts any upload size, doesn't validate the email
   (`str`), and has no rate limit. → Cap the body size, use `EmailStr`, and add a
   simple per-IP limit.
10. **`gallery_meta` loads every Photo row just to count them** (`len(event.photos)`).
    → `select(func.count())`.
11. **The S3 content type is always `image/jpeg`**, including for PNG uploads.

## 3. Deploying on Vercel + Supabase — what's missing

Facts checked against vendor docs on 2026-10-15. Sources: vercel.com/docs/functions/limitations,
vercel.com/docs/limits/fair-use-guidelines, supabase.com/pricing,
supabase.com/docs/guides/auth/rate-limits, docs.fly.io/about/pricing.

### What each platform can and cannot run

| Component | Vercel | Supabase | Verdict |
|---|---|---|---|
| Web (Vite static build) | ✅ ideal | — | **Vercel** |
| Postgres | — | ✅ (+ pgvector for later) | **Supabase** |
| Photo storage (MinIO today) | — | ✅ S3 protocol, but the free tier has only 1 GB | **MinIO on the VM** (free tier too small) |
| Photographer login (magic link) | — | ✅ Supabase Auth | **Supabase**. This removes most of story 1.3 (no token table, no session signing, no login mailer) |
| FTP server (inbound TCP 21 + passive range) | ❌ functions must be HTTP, aren't always-on, no disk | ❌ | **needs an always-on box** |
| Watcher (filesystem events) | ❌ | ❌ | **always-on box**, folded into the FTP server |
| Face service (InsightFace ≈ 300 MB model, 2 GB RAM) | ⚠️ over the 500 MB Python bundle limit; needs the 5 GB "large functions" beta + Pro 4 GB, and reloads the model on every cold start | ❌ | **always-on box** |
| API (FastAPI + SSE) | ⚠️ works, but SSE gets cut at 300–800 s, and it must reach the face service over the public internet | — | **always-on box**, next to the face service |

So **Vercel + Supabase alone can't run Solna.** Cameras push over FTP, and
neither platform accepts raw inbound TCP. You need a third piece: a small
always-on container host.

### Chosen setup: all free tiers (decided 2026-10-15; the owner is the only photographer)

```
 camera ──FTP──►  Oracle Cloud Always Free ARM VM (EU region)        Supabase Free (EU)
                  ├─ ftp + ingest hook ─► minio (block volume)        ├─ Postgres
                  ├─ api (FastAPI + SSE) ──────────────────────────►  └─ Auth (magic links)
                  ├─ faceservice (private compose network)
                  └─ caddy: https://api.<sub>, https://media.<sub>
 guest phone ──HTTPS──► Vercel Hobby (web, https://<sub>)
```

- **Vercel Hobby** for the web app. It's personal use (one photographer), so it fits the plan's terms.
- **Supabase Free** for **Postgres + Auth only**. Storage stays off Supabase:
  the free 1 GB holds about 100 originals.
- **Oracle Cloud Always Free ARM VM** runs the existing docker-compose, minus
  Postgres: FTP, API, face service, MinIO, Caddy. It's the only free host that has
  enough RAM for InsightFace *and* accepts raw FTP ports.
  - 2026 limit: reportedly cut from 4 OCPU / 24 GB to 2 OCPU / 12 GB. Still plenty.
  - Free block storage holds the photos in MinIO.
  - The face service's arm64 build is already handled (`fc9da61`).
  - Fly.io has no free tier for new accounts (trial only). Railway can't do FTP
    passive port ranges.
- **Watcher folded into the FTP server** (`on_file_received`). Even on one VM this is
  the right fix for partial uploads (§2 #2), and it removes a container.

### Free-tier gotchas (and what we do about them)

| Gotcha | Mitigation |
|---|---|
| Oracle may **reclaim idle Always Free VMs** (low CPU/memory/network over 7 days) | Upgrade the account to Pay-As-You-Go. Always Free resources stay free, the reclaim rule stops applying, and a €1 budget alert catches surprises |
| Oracle ARM capacity is often "out of capacity" in busy regions | Try another availability domain/region (Marseille, Paris, Frankfurt, Amsterdam); retry later |
| **Supabase Free pauses after 7 days of inactivity**, which breaks login and galleries between events | A daily keep-alive query from the VM (cron), or un-pause by hand before an event |
| Supabase built-in mailer allows **2 emails/hour** | Custom SMTP: Resend or Brevo free tier (+ SPF/DKIM records on your domain) |
| Supabase Free DB is 500 MB | Fine. Each face embedding is about 10 KB as JSON, so tens of thousands of faces fit. pgvector (backlog 4.3) would shrink it 5× if needed |
| No managed backups on free tiers | Nightly `pg_dump` + MinIO mirror to a second free bucket (story 1.5) |

### What you need to provide

- DNS records on your domain: `<sub>` → Vercel, `api.<sub>` + `media.<sub>` → VM IP,
  plus SPF/DKIM for the mail provider.
- Accounts: Vercel, Supabase (EU region), Oracle Cloud (card needed for
  verification; PAYG upgrade recommended), Resend or Brevo.

### Code changes the move requires

1. `DATABASE_URL` → Supabase **session pooler (port 5432)**. Direct connections are
   IPv6-only, and the transaction pooler (6543) breaks psycopg prepared
   statements unless you set `prepare_threshold=None`. Alembic replaces `create_all`.
2. MinIO stays. Photos are served at `https://media.<sub>` through Caddy as
   **presigned URLs** (private bucket). Presign against the public endpoint.
3. Delete `ensure_photographer_intake_dir` from the API (§2 #8).
4. FastAPI dependency that verifies the Supabase JWT and maps it → `Photographer`,
   with an invite allowlist checked on first login.
5. CORS locked to `https://<sub>`. `VITE_API_BASE=https://api.<sub>`. A `vercel.json`
   SPA rewrite so `/g/<token>` deep links resolve.
6. `docker-compose.prod.yml`: Caddy, no Postgres, only 80/443/FTP ports public.
   FTP `masquerade_address` = the VM public IP; open the ports in the Oracle VCN
   security list *and* the VM's iptables (Oracle images block them by default).


### Operational reality to know before the first event

Cameras used to upload on the **local LAN**. Now they upload **over the
internet**: venue Wi-Fi, or the photographer's phone hotspot. A 10 MB JPEG over a
4G hotspot takes a few seconds. That's fine, but it's worth testing at the venue.
Plain FTP sends credentials in clear text over that link (backlog 4.4 covers this;
acceptable for the pilot).

- **Gallery visibility: photographer decides per event.** Each event gets a toggle:
  "matches only" (default) or "matches + full album". The bucket goes private either
  way, and photos are served as signed URLs. The all-photos endpoints stay, but answer
  only when the event's toggle is on.
- **Pilot signup: invite-only** (env-var email allowlist checked at first login).
- **Guest email: sent right after the selfie**, even with 0 matches (the gallery fills live).
- **No pilot date yet:** slices run in order; pick the event once slice 4 is live.
